# GSSAM Deployment Architecture

This repository remains the source of truth for the church website, admin CMS, member portal, and future mobile backend. The first managed validation deployment uses OpenAI Sites/Cloudflare-style hosting and serves the public church pages from `dist/server/index.js`, generated by `npm run build:sites`.

## Current validation deployment

- Platform: OpenAI Sites managed hosting.
- Runtime: Cloudflare-compatible worker generated from `scripts/build-sites-worker.mjs`.
- Source metadata: `.openai/hosting.json`.
- Public scope: home, about, ministries, events, messages, giving, contact, privacy, and portal placeholder routes.
- Persistence: none in the validation worker. Contact links use email and map links instead of storing submissions.

This keeps hosting low-ops: the platform handles the production worker runtime, TLS, deployment URL, and platform operations. ChatGPT can help maintain the site through future requested code/content changes, but it does not continuously monitor, operate, or administer the site unless asked in a new task.

## Full production web app path

The existing Next.js app builds successfully after the upload type fix. It includes public routes, admin CMS routes, member routes, cookie sessions, Prisma models, and demo seed data.

Before using the CMS/member portal with real congregation data:

- Replace SQLite with managed Postgres, Neon, Supabase, PlanetScale, or a D1-backed data access layer.
- Move uploads from `public/uploads` to managed object storage such as Cloudflare R2, S3, or Supabase Storage.
- Set a production `AUTH_SECRET` in the hosting platform, not in source control.
- Remove demo users and demo finance records.
- Keep authorization checks server-side for admin/member routes and APIs.
- Keep finance, content, and session rules in shared server modules under `src/lib` so web and mobile clients call the same backend behavior.

## Future mobile app shape

Use the web app as the backend authority rather than duplicating business logic in iOS/Android code:

- Add versioned API routes under `/api/v1`.
- Put content, finance, auth/session, and upload rules in `src/lib` service modules.
- Have the Next.js web UI and mobile app call the same service layer through the API.
- Use short-lived sessions or token exchange for mobile clients.
- Keep role checks and member data filters on the server.
- Add OpenAPI documentation once the mobile endpoints are defined.

Recommended mobile phase 1: implement read-only public content APIs for home, ministries, events, messages, and giving; then add member login and finance views after the production identity and database provider are chosen.
